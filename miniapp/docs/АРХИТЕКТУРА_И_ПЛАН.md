# Архитектура и план Telegram Mini App

Статус: проектное решение утверждено 8 августа 2026 года; этап 2 локальной backend-основы завершён. Frontend, CI/CD и production-развёртывание не начаты.

## 1. Цель и границы

Mini App — новый адаптивный интерфейс к существующему Telegram Calendar Bot. Он не создаёт вторую базу и не получает прямого доступа к Google Calendar. Бот продолжает работать без изменения текущих сценариев; Mini App и бот используют одну бизнес-логику, SQLite WAL и Google Apps Script gateway.

Первая версия включает полный пользовательский и административный функционал. Это означает один Mini App с роль-зависимыми экранами, а не два отдельных приложения. Роль администратора определяет только backend по проверенному Telegram ID; frontend не является источником полномочий.

## 2. Выбор frontend-стека

| Вариант | Состав | Плюсы | Ограничения |
| --- | --- | --- | --- |
| **A. Рекомендуемый** | React, TypeScript, Vite, React Router, TanStack Query, собственные CSS-токены | Зрелая экосистема для сложных форм, таблиц и админ-кабинета; строгая типизация; простое разделение кодовых частей по ролям; статическая сборка | Чуть больший начальный bundle, который нужно разделить по маршрутам |
| B | Vue 3, TypeScript, Vite, Vue Router, Pinia | Компактные single-file components и удобная реактивность | В проекте нет существующего Vue-кода; выигрыш относительно React для данного объёма несущественен |
| C | Vanilla TypeScript или Lit, Vite | Минимум зависимостей и небольшой bundle | Сложнее поддерживать многочисленные формы, права, таблицы, календарь и состояние; экономия на зависимости превратится в собственный framework-код |

Выбран вариант A. Сборка выполняется только на GitHub-hosted runner: `vite build` создаёт статический `dist/`, который отдаёт Nginx. Node.js не запускается на VPS. Компонентную библиотеку в MVP не добавляем: интерфейс строится на собственных CSS-токенах сайта и переменных темы Telegram, чтобы сохранить визуальный стиль и не связать проект с чужой дизайн-системой.

Публичные frontend-переменные ограничиваются, например, `VITE_API_BASE=/api/v1`; в bundle не попадают токены, ключи, URL Google Apps Script или идентификаторы пользователей.

## 3. API: варианты и решение

| Вариант | Оценка |
| --- | --- |
| **Versioned REST JSON + action endpoints** | **Выбран.** Понятные ресурсы и отдельные защищённые действия (`approve`, `offer-alternatives`, `request-change`). Легко тестировать, документировать и сохранять идемпотентность. |
| BFF с экранными endpoint'ами | Уменьшает число запросов, но слишком связывает backend с конкретной версткой. Можно применять точечно для dashboard, но не как основной контракт. |
| GraphQL | Не нужен при одном клиенте, усложнит авторизацию, аудит, ограничение полей и защиту от избыточных запросов. |

API размещается по тому же origin, что и frontend: `https://calendar.yibogdanovskaya.ru/api/v1`. Поэтому production CORS не нужен. Версия в пути позволит развивать контракт без поломки установленного Mini App.

## 4. Целевая архитектура

```text
Telegram Mini App
        |
        | HTTPS: статические HTML/CSS/JS
        v
Nginx: calendar.yibogdanovskaya.ru
        |                         \
        | /api/* (localhost)       \ / (static dist)
        v                           v
Mini App API (Python ASGI)       Vite production bundle
        |
        v
Общий domain/service layer
        |                    \
        v                     v
SQLite WAL                  Google Apps Script gateway
                               |
                               v
                         Личный Google Calendar

Существующий aiogram bot --> тот же domain/service layer
```

Рекомендуется отдельная Python ASGI-служба, доступная только на loopback и проксируемая Nginx. Это изолирует HTTP-нагрузку и ошибки API от Telegram long polling, при этом не добавляет Node.js runtime. Альтернатива — запуск API внутри процесса бота — не выбрана: его перезапуск станет одновременно недоступностью бота и Mini App.

Сейчас правила распределены между aiogram handlers, `Database`, `booking_rules`, `slots` и automation. До API потребуется вынести в общий domain/service layer операции доступности, заявки, альтернативы, переносы, ручные встречи, серии, настройки, privacy и статистику. Это изменение затронет `app/`, миграции и deploy-конфигурацию, поэтому выполняется только после отдельного согласования владельца.

## 5. Авторизация и безопасность

1. Frontend передаёт raw `Telegram.WebApp.initData` только на `POST /api/v1/auth/telegram`.
2. Backend проверяет Telegram HMAC-подпись, `auth_date`, структуру пользователя и только затем извлекает Telegram ID. Данные `initDataUnsafe` никогда не считаются достоверными.
3. Backend создаёт случайную короткую серверную сессию: cookie `__Host-calendar_session`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 30 минут с безопасным продлением при активности. В БД хранится только хэш идентификатора сессии.
4. Все изменяющие запросы требуют CSRF token, заголовок `Origin` того же домена и `Idempotency-Key`. Повтор с тем же ключом возвращает прежний безопасный результат, а не выполняет операцию повторно.
5. Доступ к объектам всегда проверяется server-side: пользователь — только свои данные; администратор — только по серверной роли. Google event ID, занятые интервалы, названия и участники чужих событий не возвращаются API.
6. Применяются rate limits по сессии/Telegram ID и IP, точный allowlist Host, HTTPS, CSP, `X-Content-Type-Options`, `Referrer-Policy` и аудит административных действий. В production отключаются интерактивные API docs.

Для реализации понадобятся обратно совместимые migration version 6: таблицы коротких Mini App-сессий и ключей идемпотентности. Миграция будет транзакционной, с резервной копией и тестированием на копии production БД.

## 6. Контракт API v1

Все ответы используют JSON и не содержат секретов или деталей внешнего календаря. Ошибки имеют вид:

```json
{
  "error": {
    "code": "SLOT_UNAVAILABLE",
    "message": "Это время уже занято. Выберите другой слот.",
    "retryable": false,
    "request_id": "..."
  }
}
```

Коды: `AUTH_REQUIRED`, `AUTH_INVALID`, `ACCESS_DENIED`, `CONSENT_REQUIRED`, `VALIDATION_ERROR`, `NOT_FOUND`, `SLOT_UNAVAILABLE`, `CONFLICT`, `IDEMPOTENCY_CONFLICT`, `RATE_LIMITED`, `EXTERNAL_UNAVAILABLE`, `INTERNAL_ERROR`.

| Группа | Основные endpoints |
| --- | --- |
| Сессия | `POST /auth/telegram`, `DELETE /auth/session`, `GET /me` |
| Политика | `GET /privacy-policy`, `POST /consents` |
| Доступность | `GET /booking-config`, `GET /availability/dates`, `GET /availability/slots?date=&duration=` |
| Пользовательские заявки | `POST /requests`, `GET /requests`, `GET /requests/{id}`, `PATCH /requests/{id}`, `POST /requests/{id}/cancel`, `POST /requests/{id}/alternatives/{alternative_id}/accept`, `POST /requests/{id}/change-requests` |
| Privacy | `POST /deletion-requests`, `POST /deletion-requests/{id}/confirm` |
| Администрирование | `GET /admin/dashboard`, `GET /admin/requests`, `POST /admin/requests/{id}/approve`, `POST /admin/requests/{id}/reject`, `POST /admin/requests/{id}/alternatives`, `PATCH /admin/requests/{id}` |
| Админ-встречи и серии | `GET,POST /admin/events`, `GET,PATCH,DELETE /admin/events/{id}`, `GET,POST /admin/series`, `GET,PATCH,DELETE /admin/series/{id}`, действия с отдельным повторением |
| Настройки и контроль | `GET,PATCH /admin/settings`, closed dates, reminders, policy version, statistics и статус Google integration |

Названия, точные поля и пагинация будут зафиксированы в OpenAPI и contract tests до UI-реализации. Слоты пересчитываются backend при каждом получении и окончательно проверяются внутри транзакции при действии, меняющем расписание.

## 7. Карта экранов

```text
Старт / проверка Telegram
  ├─ Согласие с политикой (если отсутствует)
  └─ Главная
      ├─ Записаться: длительность → дата → часть дня/слот → детали → проверка → заявка отправлена
      ├─ Мои встречи: список → карточка → редактирование pending / альтернатива / запрос переноса или отмены
      ├─ Помощь и политика
      ├─ Удаление данных: выбор варианта → последствия → подтверждение → статус
      └─ Управление (только администратор)
          ├─ Dashboard
          ├─ Заявки: список → карточка → согласовать / изменить / альтернативы / отклонить
          ├─ Ручные встречи: список → редактор → проверка конфликта → отдельное подтверждение пересечения
          ├─ Серии и отдельные повторения
          ├─ Настройки доступности, длительностей, резерва, напоминаний и закрытых дат
          ├─ Статистика
          └─ Статус Google и технические ошибки
```

На телефоне — нижняя навигация и полноэкранные последовательные формы; для администратора раздел «Управление» открывает вложенное меню. На широком экране — левая навигация, таблицы с фильтрами и параллельный просмотр списка и карточки. Во всех ветках предусмотрены loading, empty state, отсутствие сети, истёкшая сессия, повторная отправка и `SLOT_UNAVAILABLE`.

## 8. Этапы реализации

1. **Проектирование.** Утвердить этот документ, отдельный API schema, интерактивный mobile/desktop прототип и UAT.
2. **Общий backend.** После согласования изменений вне `miniapp/` выделить сервисный слой, добавить ASGI API, Telegram auth, сессии, idempotency и contract/unit tests. Существующий бот переводится на сервисы без изменения его UX. Сначала реализуется и проверяется безопасное ядро: auth/session/CSRF, доступность, базовый жизненный цикл пользовательской заявки; остальные пользовательские операции завершаются вместе с этапом 3, административные — вместе с этапом 4.
3. **Пользовательский frontend и оставшиеся пользовательские операции API.** React shell, Telegram theme bridge, policy, booking, собственные заявки, альтернативы, переносы, удаление данных и error states.
4. **Административный frontend и административные операции API.** Dashboard, обработка заявок, ручные события, серии, настройки, статистика и безопасные подтверждения опасных действий.
5. **CI/CD и изоляция dev.** Node LTS только в GitHub Actions: install, lint, type-check, unit tests, build и проверка static artifact. Отдельный preview с тестовым ботом/backend; production Environment, secrets, защита `main` и end-to-end CD завершаются только после авторизации владельца.
6. **UAT и выпуск.** Изолированная проверка, backup/rollback rehearsal, ручное подтверждение владельца и лишь затем production deploy из `main`.

## 9. Критерии приёмки

- Build создаёт только статические файлы; на VPS нет Docker и Node.js runtime.
- Проверка подписи и срока `initData` обязательна; поддельные, просроченные или отсутствующие данные не дают сессию.
- Пользователь не получает чужие заявки или любые детали личного Google Calendar; API и UI проходят negative tests на IDOR.
- Пользовательский и административный сценарии соответствуют правилам действующего бота, включая consent, сроки, окно записи, резервы, альтернативы, переносы, удаления и напоминания.
- Два одновременных запроса не создают два активных резерва или события; повтор mutation с тем же `Idempotency-Key` не создаёт дубль.
- Бот проходит полный существующий Python test suite без изменения текстов, кнопок и навигации; новые API/domain tests и frontend tests проходят в CI.
- Интерфейс проверен в Telegram Android/iOS/Desktop и обычных современных браузерах на телефоне, планшете и компьютере.
- Ошибки Google/сети/сессии дают понятное сообщение без технических деталей; действия администратора аудитируются.
- Deployment имеет проверенный backup, health-check, rollback и не перезапускает существующий сайт/Nginx при обычном обновлении бота.

## 10. Открытая инфраструктурная зависимость

CI уже выполняет Python-проверки. Перед production Mini App остаются обязательными авторизация владельца в GitHub, создание Environment `production`, ограниченные secrets, required reviewer, защита `main` и end-to-end CD. До завершения этих действий production deployment не выполняется.
