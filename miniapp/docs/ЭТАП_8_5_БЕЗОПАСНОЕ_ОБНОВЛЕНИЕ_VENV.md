# Этап 8.5 — безопасное обновление Python virtualenv

Статус: подготовлен и проверен 9 августа 2026 года. Изменения находятся в `dev`; рабочая production virtualenv не переключалась.

## Решение

При неизменном `requirements.txt` deploy продолжает использовать текущую `/opt/calendar-bot/.venv`.

Если зависимости изменились, deploy делает следующее **до остановки служб**:

1. создаёт `/opt/calendar-bot/.venv.next-<timestamp>` от пользователя `calendarbot`;
2. устанавливает зависимости из release-кандидата и выполняет `pip check`;
3. выполняет compilation и Python tests кандидата новой средой;
4. только при успешных проверках останавливает службы, делает backup базы и переключает каталоги virtualenv;
5. прежняя среда сохраняется как `/opt/calendar-bot/.venv.previous-<timestamp>`.

При любой ошибке после переключения rollback возвращает предыдущий каталог `.venv`, удаляет неактивную candidate virtualenv, восстанавливает код/статику/базу и запускает прежние службы. Предыдущая venv не удаляется автоматически после успешного выпуска: она остаётся быстрым резервом до отдельного подтверждения итоговой очистки.

## Проверка

На VPS выполнена изолированная проверка в закрытом rehearsal-каталоге:

- создана пустая «прежняя» virtualenv и новая virtualenv с требованиями Mini App;
- новая среда успешно прошла `pip check` и проверку наличия FastAPI/uvicorn;
- выполнено атомарное переключение каталогов;
- выполнен rollback к прежней среде;
- весь временный каталог и переданный `requirements.txt` удалены.

Рабочая `/opt/calendar-bot/.venv`, рабочий бот, preview, Nginx и production SQLite в этой проверке не изменялись.

## Ограничение до финального выпуска

На VPS пока работает ранее установленная версия restricted deploy script. До production release отдельно проверяется и, после явного подтверждения владельца, обновляется именно этот server-side deploy entrypoint до версии из `deploy/deploy_from_stdin.sh`. Нельзя рассчитывать, что один лишь merge в `main` автоматически заменит уже установленный restricted entrypoint.
