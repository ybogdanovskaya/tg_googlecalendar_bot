## Гарантии решения

- Node.js используется лишь в GitHub Actions. На VPS нет Node.js runtime и Docker.
- Frontend bundle из `miniapp/dist` создаётся заново только на CI и сохраняется в `/opt/calendar-bot/miniapp-static` с правом Nginx на чтение.
- API и бот читают один и тот же закрытый production env и работают с одной SQLite WAL базой.
- Дополнительный файл `/etc/calendar-bot/calendar-miniapp.env` не содержит токенов: он задаёт только API host/port, secure-cookie и путь лога. Основные секреты продолжают находиться в существующих закрытых файлах `/etc/calendar-bot/` и `/var/lib/calendar-bot/`.
- API не публикуется наружу напрямую: внешним входом служит только Nginx HTTPS. Внутренний health-check обращается к `127.0.0.1:8001/api/v1/health`.
- При ошибке после переключения deploy восстанавливает сохранённые код, статику и базу, затем возвращает рабочий бот. Если Mini App работал до обновления, он также будет возвращён и проверен.

## Предварительный порядок P2.3

После отдельного подтверждения владельца следующий инфраструктурный этап будет выполнен малыми проверяемыми шагами:

1. Владелец создаёт DNS A-запись `calendar` на VPS и сообщает, когда она опубликована.
2. Я проверяю DNS и существующие Nginx/systemd конфигурации только на чтение.
3. На VPS устанавливаются value-free templates и дополнительный env-файл; существующий `calendar-bot.env` и его секреты не переписываются.
4. Получается TLS-сертификат, выполняется `nginx -t`, затем точечный `nginx reload` только после успешной проверки.
5. На изолированной копии production SQLite проверяются migrations и одновременная работа bot/API.
6. Только затем кандидат проходит PR `dev` → `main`, CI, отдельное подтверждение merge и отдельное ручное подтверждение production deploy.
