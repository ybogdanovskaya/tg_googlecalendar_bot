# Этап 8.1 — проект production-маршрута Mini App

Статус: спроектирован 9 августа 2026 года. Документ фиксирует решение для будущего выпуска, но **не разрешает** менять `main`, DNS, VPS, Nginx, systemd, рабочий бот, production SQLite или личный Google Calendar.

## 1. Зафиксированное решение

Mini App остаётся **Telegram-only**:

- открывается из рабочего Telegram-бота в Telegram Mobile, Desktop или Web;
- обычный браузер без Telegram не является способом входа и показывает понятное сообщение;
- сервер принимает запросы только после проверки подписанных Telegram `initData`;
- отдельные пароль, регистрация, вход по email и браузерная сессия не создаются.

Это устраняет вторую систему авторизации и не добавляет хранение паролей или персональных данных. Возможность самостоятельного браузерного кабинета может быть добавлена позднее отдельным проектом, не меняя это решение.

## 2. Фактическое состояние на начало этапа

Проверено только чтением конфигурации и сети:

| Область | Состояние |
| --- | --- |
| Рабочий бот | Активен, использует `/opt/calendar-bot`, `calendar-bot.service` и production SQLite. |
| Preview Mini App | Изолирован: отдельные test-бот, база, Apps Script, сервис на `127.0.0.1:8002` и домен `calendar-dev.yibogdanovskaya.ru`. |
| Production-домен | Для `calendar.yibogdanovskaya.ru` на момент проверки нет A-записи; Nginx server block отсутствует. |
| Свободный порт | `127.0.0.1:8001` не занят; он выбран для production Mini App API. |
| Текущий CD | Разворачивает только Python-часть рабочего бота: не собирает Vite bundle, не включает `miniapp/` в release archive и не управляет Mini App service. |

Никаких значений секретов, production-конфигураций или данных календаря при этой проверке не выводилось и не менялось.

## 3. Целевая схема

```text
Пользователь Telegram
        │ подписанные initData
        ▼
https://calendar.yibogdanovskaya.ru
        │
        ├─ /        → Nginx → статический Vite bundle
        └─ /api/    → Nginx → 127.0.0.1:8001
                                      │
                                      ▼
                          calendar-miniapp.service
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
      единая Python бизнес-логика              production SQLite WAL
      в /opt/calendar-bot                    /var/lib/calendar-bot/...
                 │
                 ▼
     существующий Google Apps Script gateway
```

### Почему API размещается рядом с ботом

Рекомендуется не создавать вторую production-базу и не поддерживать отдельную копию backend-кода. Новый `calendar-miniapp.service` будет запускать `app.miniapp_api` из того же release-каталога `/opt/calendar-bot`, что и рабочий бот. Обе службы используют одну проверенную версию бизнес-логики и одну SQLite-базу в режиме WAL.

Это не означает, что Mini App получает данные личного Calendar: API отдаёт лишь занятость слотов и данные пользователя, определённые контрактом API. Административная роль определяется сервером по Telegram ID.

## 4. Что будет создано в P2.2

После отдельного согласования изменений **вне `miniapp/`** будут подготовлены и проверены в ветке `feature/miniapp-production-*`:

1. `calendar-miniapp.service`: пользователь `calendarbot`, loopback `127.0.0.1:8001`, жёсткие systemd-ограничения, отдельный лог Mini App, общий release-каталог и production SQLite.
2. Закрытое дополнение к `/etc/calendar-bot/calendar-bot.env`: только имена путей и параметры `MINIAPP_API_BIND_HOST=127.0.0.1`, `MINIAPP_API_BIND_PORT=8001`, `MINIAPP_COOKIE_SECURE=true`. Новые секреты не нужны: API безопасно использует уже существующие закрытые файлы рабочего бота и не копирует их в GitHub.
3. Production Nginx site: TLS-домен `calendar.yibogdanovskaya.ru`, static root, `/api/` reverse proxy, `try_files`, защита скрытых файлов, базовые заголовки и кеширование только хешированных ассетов. Существующие сайты и preview не перезапускаются и не изменяются.
4. Production workflow: Node.js используется только в GitHub Actions для `npm ci`, тестов и `npm run build`. Готовый `dist` включается в release archive; постоянного Node.js-процесса или Docker на VPS не появится.
5. Deploy/rollback: архивируются прежние Python-файлы и статика; перед переключением создаётся backup SQLite; bot и API переключаются согласованно; при неуспехе восстанавливаются предыдущие код, статика, база и обе службы.

## 5. Внешнее действие владельца в P2.3

Когда P2.2 будет готов и проверен, потребуется одно действие в панели домена:

| Что создать | Значение |
| --- | --- |
| DNS A-запись | Имя `calendar`, IP-адрес того же VPS, что обслуживает рабочий бот и preview. |

После распространения DNS я смогу запросить TLS-сертификат и включить новый Nginx site. Точный IP не записывается в Git и не нужен в этом документе. До отдельного подтверждения владельца DNS не меняется.

## 6. Контрольный порядок будущего выпуска

1. Реализовать P2.2 только в feature-ветке, без production-изменений.
2. Пройти CI: Python, frontend tests/build и scanner секретов.
3. Проверить миграции и совместную работу bot/API на свежей копии production SQLite, без пользовательского доступа.
4. Получить A-запись и TLS, затем проверить Nginx config до reload.
5. Создать PR `dev` → `main`; merge и запуск production workflow выполняются только после отдельного подтверждения владельца.
6. После ручного GitHub Environment approval проверить: bot service, Mini App service, HTTPS, `/api/v1/health`, логи, backup, роль администратора, пользовательский вход и отсутствие утечки Calendar.

## 7. Стоп-условия и откат

Выпуск останавливается и выполняется откат, если не проходит хотя бы одно условие:

- нет валидной DNS A-записи или TLS;
- проверка `initData`, ownership, CSRF, health endpoint или бизнес-логика API не проходит;
- миграция не проверена на копии базы;
- одна из двух служб не активна после переключения;
- Nginx config не проходит проверку;
- есть риск затронуть существующий сайт, preview, рабочий бот или раскрыть Calendar.

Откат возвращает предыдущую версию кода и статики, восстанавливает backup базы только при необходимости и запускает обе службы. Никакого удаления production-данных не предусматривается.
