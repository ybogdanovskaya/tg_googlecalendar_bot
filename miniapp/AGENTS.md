# Правила разработки Mini App

Этот файл дополняет корневой `AGENTS.md` и действует для всей папки `miniapp/`.

## Порядок начала

1. Прочитать `../AGENTS.md`, `../PROJECT_CONTEXT.md`, `../CI_CD_инструкция.md` и `README.md` этой папки.
2. До программирования согласовать MVP scope, карту экранов, frontend-стек, API и критерии приёмки.
3. Работать в `dev` или `feature/miniapp-*`.

## Границы

- Все frontend-исходники и frontend-тесты размещать в `miniapp/`.
- Не менять существующий Telegram-бот, backend, Google Apps Script, базу или серверную конфигурацию без явного обоснования и согласования.
- Не дублировать правила слотов, статусов и встреч в frontend; источником истины должен быть backend.
- Не создавать вторую production-базу для Mini App.
- Не добавлять Docker и постоянный Node.js runtime без отдельного архитектурного решения.

## Безопасность

- Не хранить секреты во frontend и Git.
- Обязательно проверять Telegram `initData` на backend.
- Не считать Telegram ID, имя, email или роль администратора достоверными без серверной проверки.
- Не передавать пользователю содержимое Google Calendar; API возвращает только допустимые свободные слоты и данные самого пользователя.
- Все изменяющие операции защищать от повтора и конкурентного выполнения.

## UX

- Основной сценарий оптимизировать для мобильного Telegram.
- Русский язык — первый; тексты не должны препятствовать будущей локализации.
- Сохранять согласованные правила: длительности, окно пользователя, утро/день/вечер, подтверждение и статусы.
- Обязательно предусмотреть состояния загрузки, пустого результата, потери сети, занятого слота и повторной отправки.

## Сборка и выпуск

- Сборка выполняется в GitHub Actions.
- На VPS публикуются только статические production-файлы.
- Preview из `dev` не должен изменять работающий production Mini App.
- Production-развёртывание выполняется из `main` после ручного подтверждения.
- После каждого решения обновлять `README.md` этой папки и при необходимости `../PROJECT_CONTEXT.md`.
