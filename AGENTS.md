# Правила работы с проектом

Область действия этого файла — весь репозиторий Telegram Calendar Bot, включая будущий Mini App.

## Перед началом работы

1. Полностью прочитать `PROJECT_CONTEXT.md`, `README.md` и документы, относящиеся к задаче.
2. Проверить текущую ветку и состояние Git. Новая разработка ведётся в `dev` или в `feature/*`, но не напрямую в `main`.
3. Сохранить работоспособность существующего Telegram-бота, Google Calendar, сайта и серверных регламентных операций.
4. Не начинать production-развёртывание без отдельного подтверждения владельца.

## Ветки и выпуск изменений

- `feature/*` — отдельная доработка;
- `dev` — интеграция и пользовательское тестирование;
- `main` — проверенная production-версия;
- допустимый маршрут: `feature/*` → `dev` → `main`;
- перенос в `main` выполняется только после успешного CI и подтверждения владельца;
- production CD запускается вручную из `main`.

## Защита работающего продукта

- Не менять внешний вид, тексты, кнопки и навигацию действующего Telegram-бота без явного согласования.
- Не удалять и не преобразовывать production-данные без проверенной резервной копии и плана отката.
- Миграции SQLite должны быть обратно совместимыми, транзакционными и протестированными на копии действующей базы.
- Перед развёртыванием проверять приложение в изолированной среде.
- После развёртывания проверять службу, журнал, базу, Google Apps Script и штатный health-check.
- Сайт и Nginx нельзя перезапускать при обычном обновлении Telegram-бота.

## Обязательные проверки

Для Python-части:

```bash
python scripts/check_repository_secrets.py
python -m compileall -q app scripts tests
python -m unittest discover -s tests -v
```

При добавлении Mini App в CI должны появиться отдельные проверки сборки, типов, тестов и статических файлов frontend.

## Архитектурные ограничения

- Production: Python 3.12, aiogram 3, Telegram long polling, SQLite WAL, Google Apps Script, systemd и Nginx.
- Docker в текущем проекте не используется и без отдельного решения добавляться не должен.
- VPS маломощный: Mini App проектируется как статический frontend, собираемый в GitHub Actions.
- Постоянный Node.js-процесс для Mini App на production не использовать; Node.js допустим только на CI-сборке.
- Mini App должен использовать существующий backend и единую бизнес-логику, а не отдельную независимую базу.
- Пользователь не должен получать доступ к содержимому личного Google Calendar администратора.

## Секреты и персональные данные

- Не читать и не выводить значения секретов без необходимости.
- Не добавлять в Git токены, приватные SSH-ключи, OAuth-файлы, URL и общий секрет Google Apps Script, production-базу или журналы.
- Для GitHub Actions используется отдельный ограниченный deploy-ключ; личный SSH-ключ владельца не используется.
- Telegram Mini App обязан проверять `initData` на backend; данным клиента без серверной проверки доверять нельзя.
- Изменения состава и срока хранения персональных данных требуют обновления политики конфиденциальности.

## Документирование

- После архитектурного решения обновлять `PROJECT_CONTEXT.md` и документацию Mini App.
- После изменения сервера обновлять внешний паспорт VPS.
- В документах не указывать значения секретов и личные идентификаторы.
