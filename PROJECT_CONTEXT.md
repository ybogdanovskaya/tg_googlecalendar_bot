# Контекст проекта Telegram Calendar Bot

Актуальность снимка: 8 августа 2026 года.

## 1. Назначение

Сервис позволяет пользователям запрашивать встречу с владельцем личного Google Calendar, не раскрывая им содержимое календаря. Владелец согласовывает, отклоняет, переносит и создаёт встречи через Telegram.

Основной язык — русский. Часовой пояс — `Europe/Moscow`.

## 2. Реализованный продукт

- Telegram-бот доступен любому пользователю по ссылке.
- Обязательные данные заявки: имя Telegram, email и тема.
- Описание и место/ссылка необязательны.
- Длительности: 15, 30, 45, 60 и 90 минут.
- Для пользователей действует настраиваемое окно записи, по умолчанию `08:00–21:00`; встреча должна полностью закончиться внутри окна.
- Пользователь выбирает дату, затем утро, день или вечер с количеством свободных слотов.
- Администратор может создавать встречи и неблокирующие события в любое время, с гостем или без него, в том числе с подтверждённым пересечением.
- Реализованы согласование, отклонение, редактирование pending-заявок, альтернативы, переносы, отмены и повторное подтверждение.
- Реализованы ручные и повторяющиеся встречи администратора, управление серией и отдельными повторениями.
- Реализованы напоминания, сверка с Google, статистика, retention и подтверждаемое удаление данных.

Подробные бизнес-требования находятся в `ТЗ_Telegram-бот_Google-Calendar_v1.1.md` и документах релизов A–D.

## 3. Действующая архитектура

```text
Пользователь Telegram
        ↓
Telegram Bot API, long polling
        ↓
Python/aiogram application
        ├── SQLite WAL
        └── защищённый Google Apps Script gateway
                         ↓
                  Google Calendar
```

Production-компоненты:

- Python 3.12 и aiogram 3;
- SQLite, схема версии 5, release marker `release-d`;
- Google Apps Script как закрытый шлюз к одному личному календарю;
- systemd-служба `calendar-bot.service`;
- timers для backup, retention и health-check;
- JSONL-журнал с ежедневной ротацией;
- Nginx обслуживает существующий статический сайт независимо от бота.

Основные серверные каталоги:

- приложение: `/opt/calendar-bot`;
- закрытая конфигурация: `/etc/calendar-bot`;
- база и backup: `/var/lib/calendar-bot`;
- журналы: `/var/log/calendar-bot`.

Точные реквизиты доступа находятся во внешнем паспорте сервера и не должны переноситься в публичный репозиторий.

## 4. Ограничения VPS

Последняя проверка:

- RAM: около 960 MiB;
- доступная память: около 427 MiB;
- лимит памяти Telegram-бота: 220 MiB;
- свободный диск: около 4.9 GB;
- приложение с окружением: около 183 MB.

Вывод: Telegram-бот, существующий статический сайт и статический Mini App помещаются на VPS. Постоянный Node.js runtime, Docker или тяжёлая отдельная база без увеличения ресурсов не рекомендуются.

На сервере обнаружен отдельный Node.js-процесс с потреблением около 41 MiB. Перед добавлением любого нового постоянного runtime необходимо выяснить его назначение.

## 5. Git и CI/CD

Репозиторий: `ybogdanovskaya/tg_googlecalendar_bot`.

- `dev` — ветка дальнейшей разработки;
- `main` — production-ветка;
- обе ветки находятся на commit `c84d1be`;
- CI запускает Python 3.12, проверку зависимостей, сканирование секретов, компиляцию и 77 тестов;
- первые CI-запуски в `dev` и `main` завершились успешно;
- workflow production CD запускается только вручную из `main`;
- на VPS создан ограниченный пользователь `caldeploy`;
- установлен root-owned сценарий `/usr/local/sbin/calendar-bot-deploy-from-stdin`;
- deploy-ключ не предоставляет обычный shell-доступ;
- серверный сценарий проверяет архив, повторяет тесты, создаёт backup, запускает health-check и выполняет откат при ошибке.

### CI/CD ещё не завершён

Нужно выполнить:

1. авторизовать GitHub CLI под владельцем репозитория;
2. создать GitHub Environment `production`;
3. добавить environment secrets для ограниченного SSH-доступа;
4. назначить владельца required reviewer;
5. включить защиту `main` и обязательный CI;
6. выполнить end-to-end CD текущей версии;
7. обновить внешний паспорт сервера.

До завершения этих пунктов не считать production CD полностью готовым.

Работающий бот обновлялся вручную до добавления CI/CD. Его прикладной код соответствует commit `dfeae5f`; commits `079d1df` и `c84d1be` добавляют только CI/CD-инфраструктуру.

## 6. Целевая архитектура Mini App

```text
Telegram Mini App
        ↓ HTTPS
Статические HTML/CSS/JS-файлы через Nginx
        ↓ HTTPS API
Общий Python backend и единая SQLite-база
        ↓
Существующая бизнес-логика и Google Apps Script
```

Принятые направления:

- исходники Mini App размещаются в `miniapp/` этого репозитория;
- production получает только результат статической сборки;
- Node.js используется на GitHub-hosted runner, но не работает постоянно на VPS;
- Docker не требуется;
- рекомендуется отдельный поддомен, например `app.yibogdanovskaya.ru`;
- Mini App и чат-бот должны использовать единые правила доступности, статусы и данные;
- Telegram `initData` проверяется сервером;
- содержимое Google Calendar пользователям не раскрывается;
- русский язык — MVP, архитектура готовится к английскому.

Статус реализации на 9 августа 2026 года:

- frontend и API Mini App реализованы и проверены локально; frontend CI в `dev` работает;
- для изолированного preview подготовлены отдельные тестовые Telegram Bot, Google Calendar и Apps Script gateway, а также DNS-имя `calendar-dev.yibogdanovskaya.ru`;
- начат отдельный этап создания preview на VPS: он использует самостоятельные каталоги, SQLite, systemd-службу и Nginx server block, не затрагивая working bot и production;
- production-развёртывание, `main`, GitHub Environment/secrets и end-to-end CD остаются отдельными незавершёнными вопросами и требуют авторизации владельца.

## 7. Что ещё нужно спроектировать для Mini App

- точный MVP scope и роли интерфейса;
- карта экранов и переходов;
- выбор frontend-стека;
- контракт HTTP API;
- серверная проверка Telegram-авторизации;
- CSRF/CORS, rate limiting и правила сессии;
- одновременная работа чат-бота и Mini App с одной заявкой;
- обработка устаревших слотов и конкурентного бронирования;
- обновление политики конфиденциальности;
- поддомен, TLS и Nginx-конфигурация;
- frontend CI, preview для `dev` и production CD;
- критерии UAT и план отката.

## 8. Главный принцип дальнейшей разработки

Mini App является новым интерфейсом к существующей системе, а не отдельным продуктом с дублирующей бизнес-логикой. Любая доработка сначала проверяется в `dev`; существующий Telegram-бот и сайт должны продолжать работать без изменений.
